## ■테스트 코드

: 코드가 의도대로 잘 동작하고 예상치 못한 문제가 없는지 자동 검증하는 코드

- 무엇을 검증해야 좋은 테스트인가?
    - **반환값/상태코드/응답 바디**: API면 HTTP status, JSON 필드
    - **부작용(side effects)**: DB 레코드 생성/수정/삭제, 이벤트 발행, 파일 생성 등
    - **에러 처리**: 잘못된 입력에서 올바른 에러/메시지/코드가 나오는지
    - **권한/인증**: 토큰 없을 때 401, 권한 없을 때 403 등
    - **경계값/예외값**: 빈 값, 최대 길이, 잘못된 타입/형식(특히 API는 여기서 문제 자주 발생)
- 검증 예시
    
    **(A) 성공 케이스**
    
    - 예: test_users.py의 “내 정보 조회”는 기본 `mock_db.get_user_by_id = None`(=DB에 사용자 없음) 상태에서도 200을 기대
    
    핵심은 **상태 준비(모킹) → API 호출 → status/json assert**
    
    **(B) 예외/권한 케이스**
    
    - 인증 없이 401 확인
      - 예: `client_no_auth`로 호출 (test_users.py의 test_get_me_unauthorized)
    - 리소스 없음 404 확인
      - 예: `mock_db.get_team_by_id = None`로 두고 404 기대 (test_matching.py의 not_found 케이스)
    - 권한 없음 403 확인
      - 예: `mock_db.is_team_leader = False`로 두고 403 기대
    
    **(C) 케이스별 DB 응답만 바꿔서 로직 분기 테스트**
    
    예: test_dashboard.py
    - mock_db.get_user_stats / mock_db.get_user_activities의 반환값을 상황별로 바꿔서
    - /api/v1/dashboard/* 응답 구조가 원하는 형태로 나오는지 검증
- 좋은 테스트 코드를 위한 실전 규칙
    - **하나의 테스트는 하나의 이유로 실패하도록**: 실패 원인을 좁히기 쉬움
    - **외부 의존성 최소화**: 네트워크/실제 DB는 느리고 불안정 → 필요할 때만 통합/E2E로
    - **결정론적(deterministic)으로**: 시간/랜덤/순서 의존 제거(필요 시 seed 고정)
    - **Given-When-Then을 이름에 반영**:
        
        예: `test_get_dashboard_returns_403_when_not_admin`
        
        *엥 이렇게 403까지 세부적으로 체크? 실제 사례 찾아보기*
        
    - **테스트는 문서다**: “이 시스템이 어떻게 동작해야 하는지”를 가장 정확히 설명하는 예시가 됨

## ■테스트 종류

### **단위 테스트(Unit)**

- 함수/클래스/모듈 단위로 **외부 의존성(DB/네트워크)**을 최대한 제거(=mock)해서 빠르게 검증
- 장점: 빠름, 실패 원인 좁히기 쉬움

### **통합 테스트(Integration)**

- DB, 외부 서비스, 여러 모듈을 함께 붙여서 ’연동’이 맞는지 검증
- 예: FastAPI 엔드포인트 호출 → DB 반영/조회까지 확인

### **E2E(End-to-End)**

- 사용자 관점(브라우저/앱)에서 처음부터 끝까지 시나리오 검증
- 보통 느리고 비용이 커서 핵심 플로우 위주로 진행

## ■백엔드(파이썬&FastAPI)에서 사용한 조합

- `pytest`: 파이썬 테스트 프레임워크
- `fastapi.testclient`: API를 테스트에서 HTTP처럼으로 호출
- `unittest.mock( patch / AsyncMock / MagicMock )`: DB 같은 의존성을 가짜로 대체

## ■pytest 라이브러리

### 파일/함수 네이밍 규칙

- 보통 test_*.py 파일, test_* 함수가 자동으로 테스트로 인식됨
- 예시: backend/tests/**`test_**users.py` 안의 `def **test_**create_user_success()`

### 가장 많이 쓰는 패턴: AAA

- **Arrange(준비)**: 데이터/상태 준비 (fixture 사용 포함)
- **Act(실행)**: 함수 호출 또는 API 요청
- **Assert(검증)**: 결과가 기대와 같은지 확인

### **주요 데코레이터**

`@pytest.**fixture`:** 테스트에 반복적으로 필요한 값이나 리소스(예: app/client, DB 세션, 인증 토큰)를 재사용 가능하게 빼놓는 기능 = **준비물**

`@pytest.mark.**parametrize**`: 하나의 테스트 함수를 **다양한 입력 값**으로 여러 번 반복 실행하여 중복 코드 없이 효율적으로 다수의 테스트 케이스를 커버

## ■**unittest 라이브러리**

: 다양한 테스트를 자동화할 수 있는 Python 표준 라이브러리

### 주요 기능

```python
from unittest.mock import patch, AsyncMock, MagicMock
```

- `patch`
    - 특정 경로의 객체를 **테스트 동안만** 가짜(mock)로 교체하는 도구
    - `with patch('app.database.db') as mock_db:` 처럼 작성 → 그 블록 안에서는 `app.database.db`가 `mock_db`로 바뀜
    - 블록을 나가면 원상복구됨(테스트 격리 보장)
- `AsyncMock`
    - `await` 되는 함수(코루틴)를 가짜로 만들 때 사용
    - 우리 코드의 경우 DB 메서드들이 async라서 `AsyncMock(return_value=...)`가 잘 맞음
    - +a. 호출 검증도 가능: `mock_db.get_user_by_id.assert_awaited_once()`, `assert_awaited_once_with(...)`
- `MagicMock`
    - 그냥 일반 mock(동기 함수/속성)에 자주 씀
    - 예: `set_auth_token`처럼 “그냥 호출만 되면 되는” 동작을 때우기 좋음

### 사용 예시

우리 프로젝트의 [conftest.py](http://conftest.py) 경우: DB 레이어를 통째로 patch해서, 라우터가 호출할 메서드들을 `AsyncMock`으로 깔아두는 방식

```python
@pytest.fixture
def mock_db():
    """DB 연동 모킹"""
    with patch('app.database.db') as mock_db:
        # set_auth_token 모킹 (아무것도 하지 않음)
        mock_db.set_auth_token = MagicMock()
        
        # 모든 DB 메서드를 AsyncMock으로 모킹
        mock_db.ensure_user_exists = AsyncMock(return_value={"id": "test-user-id-123", "email": "test@example.com"})
        mock_db.get_user_by_id = AsyncMock(return_value=None)  # 기본값: 사용자 없음
        mock_db.update_user_profile = AsyncMock(return_value=None)
        mock_db.create_activity_log = AsyncMock(return_value={"id": "log-123"})
        mock_db.get_user_stats = AsyncMock(return_value={
            "total_assessments": 0,
            "active_teams": 0,
            "latest_score": None,
            "project_completion_rate": 0.0,
            "streak_days": 0,
            "longest_streak": 0,
            "already_checked_in_today": False,
        })
        ...(생략)...
```

## ■conftest.py

: 사실상 테스트의 뼈대

- **`mock_db` fixture**: `patch('app.database.db')`로 DB 객체를 통째로 가짜로 바꾸고, 라우터에서 호출할 메서드들을 기본값으로 `AsyncMock` 설정
- **`client` fixture**: get_current_user 의존성을 오버라이드해서 “항상 로그인된 사용자”로 테스트
- **`client_no_auth` fixture**: 인증 필요 없는 엔드포인트나 401 테스트용)

## ■테스트 추가하는 법

1. 테스트 파일 찾기/생성: backend/tests/test_<도메인>.py
2. 준비(Arrange)
    - 인증 필요한 API면 `client`, `auth_headers`, `mock_db` 사용
    - 인증 에러 테스트/헬스체크면 `client_no_auth` 사용
    - 해당 엔드포인트가 호출할 DB 메서드를 찾아서 `mock_db.<method> = AsyncMock(return_value=...)`로 셋업
3. 실행(Act)
    1. GET: `client.**get**("/api/v1/...", headers=auth_headers, json=...)`
        - 예시
            
            ```python
            def test_get_me(client, auth_headers, mock_user, mock_db):
                """현재 사용자 정보 조회 테스트"""
                response = client.get("/api/v1/users/me", headers=auth_headers)
            ```
            
    2. POST: `client.**post**("/api/v1/...", headers=auth_headers, json=...)`
    3. PATCH: `client.**patch**("/api/v1/...", headers=auth_headers, json=...)`
    4. DELETE: `client.**delete**("/api/v1/...", headers=auth_headers, json=...)`
4. 검증(Assert)
    - `response.status_code`가 원하는 상태코드인지 확인
        - 예시
            
            ```python
            assert response.status_code == status.HTTP_200_OK
            ```
            
    - `response.json()`에 필수 필드/값 존재하는지 확인
        - 예시
            
            ```python
                data = response.json()
                assert data["id"] == mock_user["id"]
                assert data["email"] == mock_user["email"]
                assert "profile" in data
            ```
            
    - (추천) DB 메서드가 호출됐는지까지 검증: mock_db.<method>.assert_awaited_once() 같은 형태
5. 테스트 케이스 실행
    
    backend/ 루트에서 명령어 실행
    
    ```python
    uv run pytest
    ```
